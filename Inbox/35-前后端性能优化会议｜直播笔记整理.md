# 35-前后端性能优化会议｜直播笔记整理

这场课围绕前后端性能优化展开：从架构选型、SPA/MPA、浏览器渲染、Core Web Vitals、性能监控 SDK、用户行为回放，到 Node 内存、QPS、队列、WeakMap、Stream / Buffer。中间有 Chrome DevTools MCP、Ask Gemini、浏览器自动化工具的现场演示。

转写里有休息音乐、现场杂音和口误，这里已按技术脉络重排。

## 一句话总结

老师想表达的是：AI 能提效，但性能优化仍然绕不过基础功。前端要懂架构、资源加载、渲染流水线、Web Vitals 和监控 SDK；后端尤其是 Node 要懂内存、QPS、队列、GC、WeakMap、Stream / Buffer。现在可以用 AI 辅助分析，但不能把 AI 当成替代理解的借口。

## 1. 性能优化为什么仍然重要

老师开场说，AI 很强，但开发者仍然躲不开性能指标。性能这件事在他十几年从业经历里一直存在。

但性能优化有一个“天敌”：ToB 项目。

原因是：

- 很多 ToB 项目只要能跑，老板就不关心性能。
- 团队负责人也很难主动推动性能指标。
- ToB 内部系统的用户量、访问频次、体验压力通常不如 ToC。
- 很多开发者工作多年也没真正接触过大规模性能优化。

性能优化最容易出现的场景：

- 企业真正遇到性能问题。
- ToC 大流量项目。
- 大型复杂项目。
- 首屏、交互、转化率直接影响业务。
- 线上事故、客户部署、资源成本压力。

AI 可以帮助分析，但底层思路仍然要懂。

## 2. 开发前先定架构，架构迁移代价很大

老师强调：性能优化之前，第一件事是确定架构。

如果用 [[Better-T-Stack]] 这类预设好的全栈框架，很多场景已经整合进去了，压力会小一些；如果脱离框架自己做技术选型，就必须清楚：

- 项目服务谁。
- 后续会长成什么样。
- 是否需要服务端渲染。
- 是否需要后端深度绑定。
- 是否需要本地部署、私有化或云部署。
- 是否需要多端、多服务、微服务和监控。

老师提醒：项目后期从一个架构迁移到另一个架构，代价可能是毁灭性的。因此最好一开始就想清楚。

## 3. SPA：简单、便宜，但性能天生吃亏

老师复盘了 [[SPA]] 的加载路径：

1. 浏览器先拿到 `index.html`。
2. 再加载主 JS。
3. 主 JS 拉核心库和打包后的 `main.js`。
4. 如果有异步 chunk，再继续拉异步包。
5. JS 执行生命周期。
6. 前端框架走 Virtual DOM diff / runtime。
7. 页面最终渲染出来。

SPA 的好处：

- 简单。
- 开发成本低。
- 部署方便。
- 打包成 `dist` 后可以直接放到 S3。
- 配合 CloudFront / CDN 就能上线。

SPA 的性能痛点：

- JS 文件大。
- 异步 chunk 仍需网络加载。
- 生命周期和 diff 有运行时成本。
- 首屏要等 JS 下载、解析、执行。
- Vue / React 组件和框架本身可能达到几百 KB。

老师提到，近几年一些框架尝试去 runtime、去 DOM diff，背后也是为了解决 SPA 运行时成本问题。

## 4. CDN / S3 / CloudFront 是基础部署能力

老师用 SPA 部署举例：

- 静态资源放 S3。
- 通过 CloudFront 做 CDN。
- 前端项目可以很快上线。

面试里如果被问“有没有配置过 CDN”，不能只说“用过”，最好能讲：

- 静态资源如何上传到对象存储。
- CDN 如何回源。
- 缓存策略如何设置。
- 资源版本如何通过 hash / MD5 管理。
- gzip / Brotli 如何配合。

## 5. MPA / Node 架构：需要懂后端和运维

老师提到 [[MPA]] 或纯 Node 环境时，重点不是页面本身，而是服务端运行能力：

- 要懂 PM2。
- 要懂远程服务器环境。
- 要懂 Node 运行时。
- 要懂日志、进程、内存和故障处理。
- 要懂后端基础，否则出了问题会很难排。

Serverless 通常是 stateless function，而自建 MPA / Node 服务是长期运行的服务进程，运维复杂度更高。

他还提到 Node.js + Hono、可能还有 Nest.js / 其他框架，以及自己开发服务的选择。核心不是框架名，而是要知道项目未来复杂度和架构边界。

## 6. AI 项目不是 Demo：代码量和真实复杂度要能讲

老师现场统计了自己的项目代码量：monorepo 里包含 App、Native、Server、Docs、Admin、后端 API 等多个模块，代码量已经很大。

他的面试表达重点是：

- AI 写的项目不一定只是 demo。
- 如果项目超过几万行，且有多端、多服务、后台和 API，就有真实复杂度。
- 面试官问“是不是玩具项目”时，要能说清模块、代码量、业务复杂度和部署结构。

注意：代码量不是价值本身，但能辅助说明项目不是只有几个页面。

## 7. 基础性能优化：压缩、合并、缓存、CDN

老师把“性能优化学徒工”阶段概括为一批基础动作：

- 压缩。
- 合并。
- MD5 / hash 文件名。
- 多 CDN。
- Brotli。
- gzip。
- 图片压缩。
- Webpack 预 gzip。
- 静态资源缓存。

他认为 Webpack 预 gzip 有人会当成方案，但实际收益要结合场景。它的意思是在资源返回前预先把 CSS / JS 压缩好，减少运行时压缩成本。

多 CDN 在 HTTP/1.1、HTTP/2 时代有一定意义，但在 HTTP/3 下意义会下降。不过国内很多老业务、老浏览器和老系统还没有真正用上 HTTP/3，所以面试里仍要能讲。

## 8. HTTP 缓存面试题

老师提到以前很爱考的 HTTP 缓存优先级：

- `Cache-Control`
- `Expires`
- `ETag` / `If-None-Match`
- `Last-Modified` / `If-Modified-Since`

可整理为：

- 强缓存里，`Cache-Control` 优先级高于 `Expires`。
- 协商缓存里，`ETag` 优先级高于 `Last-Modified`。
- `ETag` 适合更精确判断文件内容是否变化。
- `Last-Modified` 依赖时间精度，可能不够准确。

另一个常见题：

- HTTP/2 通过多路复用解决 HTTP/1.1 层面的队头阻塞问题。
- HTTP/2 仍然基于 TCP，仍可能有 TCP 层队头阻塞。
- HTTP/3 基于 QUIC，解决 TCP 层队头阻塞，连接迁移和弱网表现更好。

## 9. 离线缓存：从 localStorage 到 Service Worker / Workbox

老师提到以前有用 localStorage 存静态资源的方案，但现在更推荐直接使用 Workbox / Service Worker 体系。

localStorage 的特点：

- 同步读写。
- API 简单。
- 一个域通常约 5MB 限制。
- 超过 2.5MB 左右就应该监控。
- 低端机上可能有性能问题。

旧式玩法：

- 通过 iframe 指向另一个域。
- 借另一个域的 localStorage 再扩 5MB。
- 用 `postMessage` 和 iframe 通信。

这属于早期偏极客的方案，现代项目更应该优先考虑 Service Worker、Workbox、Cache Storage 和合理的版本更新策略。

## 10. 浏览器渲染：主线程、合成线程、光栅化和 GPU

老师重点讲了浏览器渲染流水线：

- 浏览器计算样式。
- 生成布局。
- 产生绘制列表。
- 主线程提交给合成线程。
- 内容拆成 tiles / 瓦片。
- 光栅化线程池处理。
- GPU 合成。
- draw call 提交给浏览器显示。

优化思路：

- 减少主线程 layout / paint。
- 尽量让动画进入合成线程。
- 利用 GPU 做 transform / opacity 等合成操作。
- 避免用会触发布局的属性做动画。

会触发合成层或 GPU 参与的常见方式：

- `transform`
- `translate3d`
- `opacity`
- `will-change`
- CSS 3D
- video
- WebGL

老师现场演示了使用 Chrome DevTools 的 Rendering / Performance 面板，看 FPS、Layers、重绘重排和 event log。用 `transform` 后，重绘过程明显减少，更多变成 commit / GPU 合成。

## 11. CSS 会影响 JS 执行

老师提到一个经典面试点：CSS 加载会影响 JS 执行。

原因是：

- JS 可能读取样式和布局信息。
- 浏览器为了保证 JS 读到正确样式，会等待 CSSOM 构建。
- 阻塞的 CSS 会拖慢后续 JS 执行和渲染。

优化方向：

- 预加载关键 CSS。
- 内联 critical CSS。
- 减少首屏阻塞 CSS。
- 拆分非关键样式。
- 延迟加载不影响首屏的样式。

## 12. 性能指标：LCP、INP、CLS 是核心

老师强调，性能优化最终要落到指标上。现在最核心的是三类 Core Web Vitals：

- [[LCP]]：Largest Contentful Paint，最大内容绘制，衡量首屏主要内容加载速度。
- [[INP]]：Interaction to Next Paint，衡量页面整体交互响应。
- [[CLS]]：Cumulative Layout Shift，衡量布局稳定性。

其他常见指标：

- FP：首次像素绘制。
- FCP：首次内容绘制。
- TTFB：首字节时间。
- TTI：可交互时间。
- TBT：总阻塞时间。
- FPS：帧率。

老师说面试里现在很喜欢问性能指标，不一定要死背所有阈值，但必须知道每个指标解决什么问题、什么情况下会变差、如何优化。

## 13. PerformanceObserver 和 Performance Timing 能做自建 SDK

老师提到，可以通过浏览器 API 自己构建性能监控 SDK。

关键 API：

- `PerformanceObserver`
- `performance.timing`
- Navigation Timing / Resource Timing 等性能数据

可采集内容：

- FP / FCP。
- LCP / INP / CLS。
- TTFB。
- DNS、TCP、TLS、请求、响应阶段耗时。
- DOMContentLoaded。
- Load。
- 资源加载耗时。
- 异常、慢接口、阻塞资源。

老师认为，现在可以让 Claude / AI 帮你生成一套 SDK，但前提是你自己要懂指标含义，否则 AI 生成了也讲不清。

## 14. 自建 Sentry / 用户行为回放的几种方案

老师讲了如何做类似 Sentry 的用户错误回放。

方案一：html2canvas 截图法

- 代理用户事件。
- 在 mousedown / click 等关键动作时用 html2canvas 把当前 DOM 转成图片。
- 转成 PNG / base64 / canvas data。
- 记录最近 20 到 35 步操作。
- 出错时把数组上传到后端。
- 后端还原成一张张图片或视频。

问题：

- 很耗流量。
- 很卡。
- 用户关闭浏览器时数据可能来不及传回。
- 记录 20 步偏少，35 步体验更连贯但成本更高。

方案二：XPath / DOM 路径法

- 记录用户点击节点的 XPath。
- 后端用 Puppeteer / 无头浏览器重新打开页面。
- 按路径重放并截图。

问题：

- 鼠标位置不天然存在，需要单独记录。
- 页面版本变化后路径可能失效。
- 还原成本较高。

方案三：rrweb 类方案

- 使用 MutationObserver 监听 DOM 变化。
- 记录虚拟 DOM 变化节点。
- 记录鼠标轨迹、点击和页面变化。
- 前端压缩成二进制 / Blob。
- 传到服务端后用 Buffer 解析并回放。

老师认为 rrweb 这类方案虽然很老，但原理仍然值得理解，因为它是更工程化的用户行为回放方式。

## 15. 数据上报：1×1 GIF / 日志服务器 / 清洗入库

老师提到自建 SDK 常见的数据上报方式：

- 前端把 JSON stringify 后的数据放到 1×1 GIF 请求的 query 里。
- 请求打到日志服务器。
- 日志服务器先便宜地存下来。
- 半夜定时清洗。
- 正常指标入库。
- 异常指标或脏数据发邮件给 SDK 开发者。

脏数据例子：

- 用户点击一个按钮，统计结果显示函数执行 15 天。
- 原因可能是 Android 用户按 Home 键离开，回来后 JS 继续执行，导致时间跨度异常。

结论：写 SDK 不只是采集数据，还要懂异常数据、平台差异、低端机、浏览器生命周期和清洗规则。

## 16. Chrome DevTools MCP：能进性能面板，但不稳定

老师现场演示了 Chrome DevTools MCP，让 AI 打开站点、跟踪 Performance、找性能问题。

优点：

- 能接近真实 DevTools Performance 面板。
- 能拿到 FCP、LCP、TTFB、资源加载、渲染阻塞等数据。
- 能分析真实页面问题。

问题：

- 连接可能不稳定。
- 多个 Chrome 账号 / 多窗口会影响连接。
- 有时会频繁断开。
- 面试现场如果工具没提前调好，会非常尴尬。

老师建议：如果要用这类工具辅助现场分析，一定提前在自己的电脑上调通，找一个最顺手的组合。

## 17. At Chrome / 浏览器插件 / Browser Use：适合操作浏览器，但不等于性能分析

老师比较了几类浏览器控制方式：

- Chrome DevTools MCP。
- At Chrome 插件。
- 浏览器自动化工具。
- Browser Use。
- Codex / VSCode 里的浏览器控制能力。

他的判断：

- 普通浏览器自动化适合“打开网站、搜索商品、加入购物车”这类操作。
- At Chrome 插件可以操作浏览器、跑 Lighthouse 或看网络信息。
- 但深度读取 Performance 面板、调 DevTools 原生数据，Chrome DevTools MCP 更合适。
- 不同工具用途不一样，不要混为一谈。

## 18. Ask Gemini：Chrome 内置分析体验更快

老师演示了 Chrome 里的 Ask Gemini / Gemini 辅助分析，认为它在性能问题定位上非常快。

它可以快速给出类似问题：

- LCP 过长。
- 第三方脚本阻塞渲染。
- CLS 布局偏移。
- 未充分利用边缘计算。
- 延迟交互问题。
- 图片原图过大，例如 4K logo 只展示 100 多像素。

老师提到：

- Chrome 本地可能有十几 GB 的 Gemini / 内置模型资源。
- 部分功能对美国节点支持更好。
- 中文站点支持比以前好。
- 需要保证 Ask Gemini 按钮或脚本可用。

整理成稳妥建议：可以把它作为页面诊断助手，但面试和工作里仍要能解释指标、原因和修复方案。

## 19. 典型前端性能问题清单

结合老师演示，可总结为：

- LCP 过长。
- 首屏大图未压缩。
- 资源原图尺寸远大于展示尺寸。
- 字体加载慢。
- CSS 阻塞 JS。
- 第三方脚本阻塞渲染。
- 缓存策略不合理。
- CLS 布局偏移。
- 首屏请求过多。
- 慢接口影响渲染。
- CDN / 边缘缓存没用好。
- 没有按需加载。
- 没有拆分关键资源和非关键资源。

## 20. Node 性能：核心是内存、QPS 和集群

后半场转到 Node。

老师认为 Node 性能最需要关注：

- 内存。
- QPS。
- 集群。
- 自动扩缩容。
- 报错和日志。

很多人以为 Node 就是 JS，分不清前端和后端边界，于是在 Node 里写出很多不适合服务端的代码，最终导致内存泄露或线上崩溃。

AI 写 Node 很方便，但上线后如果内存、IO、队列、进程数没有处理好，会很容易出事故。

## 21. Node 内存泄露：正常波动和持续上涨要分清

老师用内存曲线解释：

- 正常情况：内存上升、回收、再上升、再回收。
- 异常情况：GC 后基线仍持续向上，说明可能泄露。
- 轻则影响系统性能，重则进程崩溃。

常见导致 Node 挂掉的情况：

- IO 没处理好。
- 大文件读写卡住。
- 队列内存打满。
- 上下文里保存了过大的数据。
- `setInterval` 上一次没执行完，下一次又开始。
- 线上集群 auto scale 没跟上流量。
- PM2 进程数过多，内存被进程打爆。

## 22. QPS 要会压测，也要会合理表达

老师说面试如果写了弹性云架构、autoscale、集群，对方很可能问：

- 你们 QPS 多少？
- 怎么压测的？
- 扩容阈值是什么？
- 单机能扛多少？

建议：

- 用 `wrk` 做压测。
- 或使用 JMeter 等专业压测工具。
- 准备真实或合理的数据。
- 不要夸张到离谱，例如动辄几十万 QPS。
- 也不要小到没有讨论价值。

重点是：你要知道 QPS 是什么，怎么测，和机器、接口、缓存、数据库、队列之间是什么关系。

## 23. Map 强引用和 WeakMap 弱引用

老师用 V8 / GC 例子讲 Node 内存。

关键点：

- `global.gc()` 不是默认可用。
- 运行 Node 时需要加 `--expose-gc` 才能手动调用。
- `Map` 对 key 是强引用。
- 即使把外部变量 `key = null`，如果 Map 里还引用着它，内存仍然不会释放。
- 要释放，需要 `map.delete(key)`，同时清掉外部引用。
- `WeakMap` 对 key 是弱引用，外部引用消失后更容易被 GC 回收。

这说明：不是简单把变量置为 null 就一定释放内存，要看是否还有其他引用链。

## 24. process.memoryUsage 要知道几个字段

老师提到 Node 里常见内存字段：

- `rss`：进程常驻内存。
- `heapTotal`：V8 堆总量。
- `heapUsed`：V8 堆已使用。
- `external`：V8 管理的外部内存，常见于 Buffer。
- `arrayBuffers`：ArrayBuffer / Buffer 相关内存。

面试里不一定要背得特别细，但要知道：

- JS 对象主要在 V8 heap。
- Buffer 相关内存属于 external / arrayBuffers。
- Buffer 不完全等同普通 JS 对象内存。
- 分析 Node 内存不能只看一个字段。

## 25. 大变量、数组 push 和 Redis

老师说，Node 里常见泄露是把越来越多数据堆到一个变量或数组里：

- 不断 `push`。
- 变量越来越大。
- 内存越来越高。
- GC 无法释放，因为仍被引用。

如果数据量可能很大，不要长期放在进程内存里，应该考虑：

- Redis。
- 数据库。
- 分页。
- TTL。
- 队列。
- 流式处理。

## 26. 生产消费不及时：队列和背压很重要

老师举例：某个系统被打，触发大量错误日志。攻击或请求已经结束，但系统还在疯狂处理残留日志或任务，这就是生产消费不及时。

解决思路：

- 用 SQS / SNS / RabbitMQ / Kafka 等队列解耦。
- 请求先进队列。
- 消费端按能力处理。
- 发现大量无用任务时，可以清空或丢弃对应队列。
- 配置重试、死信队列和限流。
- 避免业务线程被日志、异步任务或突发请求拖死。

老师强调：之前讲过的 SQS、SNS、队列、削峰填谷不是概念，要真的用一用。

## 27. 闭包泄露：AI 可以审查，但你要懂原因

闭包也可能导致内存泄露：

- 闭包引用了大对象。
- 函数长期存在，导致大对象不能回收。
- 定时器、事件监听、缓存、全局变量都可能形成引用链。

处理方式：

- 移除不必要闭包。
- 解除事件监听。
- 清理定时器。
- 断开引用。
- 让 AI 帮忙审查，但自己要能判断原因。

## 28. Stream 和 Buffer：Node 性能的高级分水岭

老师最后强调：处理大数据、文件、网络流、二进制内容时，脑子里要先想到 Stream 和 Buffer。

概念：

- Stream 是流。
- Buffer 是流动的数据块。
- 大文件不要一次性读入内存。
- 流式处理可以显著降低内存峰值。
- Buffer 用得好，性能可能比普通文本处理高很多。

老师认为，普通程序员到资深程序员的一个分水岭，就是能不能熟练使用 Buffer / Stream 解决性能问题。

## 29. 作业：做一个自己的性能监控 SDK

老师布置的作业是：用 Claude / AI 帮自己设计并实现一个性能监控 SDK。

可以包含：

- 前端 Web Vitals 采集。
- FP / FCP / LCP / INP / CLS / TTFB。
- 资源加载耗时。
- JS error / unhandledrejection。
- 接口耗时。
- 1×1 GIF / Beacon 上报。
- 日志服务器。
- 数据清洗。
- 异常邮件 / 通知。
- 用户行为回放。
- Node 内存指标。
- QPS / 慢接口 / 队列积压。

目的不是做一个商业级 Sentry，而是让自己在面试里能讲清“指标怎么采、数据怎么传、异常怎么看、问题怎么归因”。

## 30. 面试表达可以这样收束

如果面试被问前端性能，可以按这个顺序回答：

1. 先看指标：LCP、INP、CLS、FCP、TTFB。
2. 再看资源：图片、字体、CSS、JS、第三方脚本、缓存。
3. 再看渲染：重排重绘、合成层、GPU、长任务。
4. 再看业务链路：接口慢、数据量大、首屏关键内容。
5. 最后说监控：SDK 采集、日志、告警、回放和复盘。

如果面试被问 Node 性能，可以按这个顺序回答：

1. 先看 QPS 和压测。
2. 再看 CPU / 内存 / GC。
3. 再看 IO、大文件、Buffer / Stream。
4. 再看队列、生产消费、背压。
5. 再看集群、PM2、容器、自动扩缩容。
6. 最后说监控和告警。
